One of the main design choices I made was splitting up what the agent can do based on the type of task. For backend actions like tracking orders and processing refunds, I used Gateway/MCP tools. For answering questions about products and catalogs, I used the Knowledge Base (KB) instead. I also added a Memory hook so the agent remembers the customer's context across different chats. I went this route because actions need strict, predictable steps, while answering questions works best when pulling from trusted documents. Keeping these separate makes the agent much more reliable and keeps it from making up fake actions.   
A real challenge I ran into was getting the MCP client connection to work right. At first, I tried a few different ways to connect, but I kept running into session conflicts and errors when the agent tried to load its tools. I figured out what was wrong by checking my logs and testing each tool-loading step one by one. I fixed it by using a context manager (with gateway_client:) and list_tools_sync() to make sure the tools were fully ready before the agent started running. Testing this locally really showed me that an agent connected to a backend won't work unless it's set up in the exact right order.
When thinking about a real-world production setup, security is a huge priority—especially setting up strict, least-privilege permissions. Since this agent connects to backend systems to do real things like tracking orders and issuing refunds, we have to be very careful. To launch this safely, the Gateway should only have permission to run the specific Lambda functions it absolutely needs. Access to the KB, memory, and browser should also be kept as tight as possible. This way, even if the agent gets confused or faces a bad input, it simply doesn't have the power to do anything it shouldn't.
